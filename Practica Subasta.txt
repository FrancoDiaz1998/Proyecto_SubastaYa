INSTITUTO DE INGENIERÍA Y AGRONOMÍACarrera: Ingeniería en InformáticaCátedra: Proyecto de SoftwareTrabajo Práctico: "SubastaYa"  "SubastaYa" es una plataforma web de subastas en tiempo real y comercio electrónico que busca modernizar las compras y ventas competitivas en línea. El modelo de negocio se apoya en dos pilares críticos:  Confianza y Solvencia Económica: En SubastaYa, toda puja debe estar respaldada por saldo real congelado en garantía (Escrow) dentro de la billetera virtual del usuario para evitar transacciones canceladas y fricción con los vendedores.  Juego Limpio (Fair Play en Subastas): Para evitar el sniping (bots o usuarios que ofertan en el último milisegundo), la plataforma incorpora un mecanismo de extensión dinámica de tiempo y una interfaz altamente reactiva donde el usuario tiene visibilidad total de las ofertas en vivo.  El objetivo del equipo de desarrollo es construir una solución web completa (Frontend, Backend y Base de Datos) que ofrezca una experiencia visual atractiva y fluida para compradores y vendedores, respaldada por un motor transaccional seguro.  1. Requerimientos Funcionales y Experiencia de Usuario (Frontend & Flujo)La aplicación web debe contar con una interfaz responsiva, intuitiva y visualmente cuidada, dividida en los siguientes módulos:  Módulo 1: Catálogo y Exploración de SubastasFiltros y Búsqueda: El usuario debe poder explorar subastas filtrando por Estado (Activas, Próximas, Finalizadas), Categoría, y Rango de precios/ordenamiento.  Cards de Producto Informativas: Cada tarjeta debe mostrar imagen referencial, título, categoría, oferta más alta actual, cantidad de ofertas realizadas y un contador regresivo visible.  Módulo 2: Creación y Publicación de Subastas (Vendedor)Formulario Interactivo: Datos del producto, configuración económica (precio base inicial y monto mínimo de incremento) y ventana temporal de inicio y fin.  Validaciones en pantalla: La fecha de finalización debe ser posterior a la de inicio, y los valores económicos deben ser positivos y coherentes.  Módulo 3: Sala de Subasta en Vivo (Live Bidding Room)Temporizador en Vivo: Reloj visual que cambie de color a amarillo/rojo al entrar en el último minuto.  Historial de Ofertas: Lista cronológica con monto, usuario anonimizado/seudónimo y hora exacta de la oferta.  Consola de Puja Dinámica: Sugerencia automática del próximo valor ($\text{Puja Actual} + \text{Incremento Mínimo}$) o posibilidad de ingresar un monto personalizado superior.  Indicador y Feedback: Indicadores visuales ("Liderando" o "Superado") y mensajes claros (toasts/modales) al confirmar puja, por fondos insuficientes o por extensión anti-sniping.  Módulo 4: Billetera Virtual y Gestión de FondosPanel de Saldo: Visualización de Saldo Total, Saldo Retenido / En Garantía, y Saldo Disponible ($\text{Saldo Total} - \text{Saldo Retenido}$).  Carga de Saldo e Historial: Formulario para acreditar saldo simulado y tabla de historial de movimientos.  Módulo 5: Panel de Usuario ("Mis Actividades")Pestañas para "Mis Compras / Pujas" (listado de subastas donde participó) y "Mis Publicaciones" (subastas creadas con métricas de recaudación).  2. Lógica de Dominio y Reglas del Negocio (Backend & Procesos)2.1 Manejo Atómico de Saldos (Garantía / Escrow): Cuando un usuario realiza la puja más alta, su saldo disponible pasa a estar retenido. Si es superado, el sistema libera automáticamente la retención del primer usuario y congela el saldo del segundo. Ambas operaciones deben ejecutarse en un bloque transaccional atómico.  2.2 Regla Anti-Sniping: Si una oferta válida se registra en los últimos 60 segundos previos al cierre, el sistema extiende automáticamente la fecha de finalización por 2 minutos adicionales.  2.3 Adjudicación y Procesos en Segundo Plano: Un proceso en segundo plano (Worker/Cron job) debe verificar subastas vencidas. Si finaliza con ganador, pasa a FINALIZADA y transfiere el saldo retenido al vendedor; si vence sin pujas, pasa a DESIERTA.  3.4 (sic) Auditoría de Eventos y Trazabilidad: Se deben registrar inmutablemente los cambios de estado de las subastas, extensiones de tiempo anti-sniping, intentos de puja rechazados y acreditaciones manuales de saldo en billeteras.  3. Lineamientos y Restricciones Técnicas3.1 Backend y Base de Datos:Stack Tecnológico: Arquitectura API REST en C# (EF Core), Java (Spring/Hibernate), Python (SQLAlchemy), Go (GORM) o Node.js (Sequelize/TypeORM).  Code-First: El esquema relacional debe generarse mediante migraciones en el código.  Preparación para Concurrencia: Incorporar mecanismos (ej. un campo Version) para soportar Optimistic Locking.  Transaccionalidad (ACID): Operaciones críticas bajo modelo transaccional con Rollback completo ante fallos.  Estándares RESTful: Diseño basado en sustantivos plurales sin verbos en URLs, uso correcto de códigos HTTP (ej. 409 Conflict para concurrencia) y documentación autogenerada (Swagger UI).  Comunicación en Tiempo Real: Sincronización de ofertas usando WebSockets (SignalR, Socket.io, etc.), o Short-Polling como alternativa mínima aceptable.  3.2 Diagrama de Base de Datos: Se sugiere un esquema relacional con tablas para Categoria, Subasta, Usuario, Billetera, Auditoria_Log, Transaccion_Ledger y Puja.  3.3 Datos Semilla Obligatorios (Seed Data):4 Usuarios (vendedor, comprador1, comprador2, sinfondos) con saldos predefinidos.  4 Categorías.  5 Subastas de prueba: Activa estándar, Activa crítica (cierra en < 2 min), Próxima, Vencida con ganador y Vencida desierta.  Registros contables que respalden los depósitos y retenciones base.  3.4 Diseño de la API REST: Endpoints mínimos de referencia incluyen GET /api/auctions, POST /api/auctions, GET /api/auctions/{id}, POST /api/auctions/{id}/bids, GET /api/wallet/balance y POST /api/wallet/deposit.  3.5 Frontend e Interfaz de Usuario: Uso de HTML/CSS/JS o frameworks modernos (React), consumo asíncrono de la API, experiencia de usuario centrada en la retroalimentación constante (spinners de carga, alertas de error) y validaciones preventivas.  3.6 Calidad de Código General: Clean Code con nomenclatura descriptiva, funciones de responsabilidad única y separación clara de responsabilidades arquitectónicas.  4. Frontend y UX (3 pts).  4.3 Auditoría de Trabajo y Calificación Individual: La evaluación es estrictamente individual. El docente auditará el historial de commits y Pull Requests. Habrá una defensa oral del proyecto, y se podrán asignar notas dispares si existe participación desigual o falta de justificación técnica.  RECURSOS:
